# Профілювання (лаба 8) — записано ДО змін у коді

Корпус: 143 книги Gutenberg, 61 МБ, 10,5 млн токенів. Python 3.13.18, Windows 11,
Ryzen 5 7500F.

Файли тут:

- `flame-index.svg`, `flame-search.svg` — py-spy flame graphs (`py-spy record
  --subprocesses`, 200/500 семплів за секунду) для `scripts/profile_targets.py index` і
  `search` (ті самі виклики, що `findex index` / `findex search`, без CLI довкола);
- `index.prof`, `search.prof` — cProfile повних команд
  `python -m cProfile -o … -m findex index data/gutenberg --executor serial` і
  `python -m cProfile -o … -m findex search index.fidx "river ship captain"`
  (відкрити: `snakeviz index.prof` або `pstats`).

скорер лаби 3 — це сотні операцій на запит.

## Python чи нативний код

**Scalene 2.4 на Windows виявився ненадійним:** з `--cpu-only` він записав порожній профіль
(`null`), а з `--profile-all` приписав 70–80 % семплів `threading.py` (власному потоку-
семплеру); для нашого коду лишилось одне сумнівне «0 % Python». `py-spy --native` на
Windows теж не допоміг: усі стеки закінчуються в C-функціях інтерпретатора, а найбільше
часу приписано імпортам модулів, що не може бути правдою. Тому розподіл Python / native
зроблено прямим експериментом — той самий текст (30 книг, 13,6 млн символів, 2,39 млн
токенів), різна кількість роботи на Python:

| що виконується | час | на токен |
|---|---|---|
| лише `TOKEN_RE.finditer` (нативний `_sre`) | 0,75 с | 314 нс |
| + `m.group()` на кожен токен | 0,88 с | 368 нс |
| `tokenize` (+ генератор, `normalize_token`, `casefold`) | 1,18 с | 492 нс |
| `Counter(tokenize(...))` | 1,37 с | 573 нс |

Токенізатор — **≈ 55 % нативного часу** (сам regex) і ≈ 45 % Python-обв'язки навколо
кожного токена. cProfile роздував частку Python: трасування додає накладні витрати до
кожного з 10,5 млн викликів.

## Три найзатратніші місця і гіпотези (до змін)

1. **Токенізація при збиранні індексу** — ≈ 75 % часу `findex index`; ≈ 55 % — нативний
   regex, ≈ 45 % — Python на кожен токен (генератор, `group`, `casefold`, `isascii`).
   *Гіпотеза:* векторизація тут не допоможе — немає масиву чисел, є 10 млн коротких рядків, а
   більше половини часу вже в C. Можна прибрати частину Python-обв'язки (`re.findall` на
   документ і `map(str.casefold, …)` у C замість генератора з `yield`), очікування — не
   більше 20–30 % на токенізації. Ціна — список токенів одного документа в пам'яті.
2. **Завантаження індексу в `findex search` / при старті сервера** — ≈ 60 % часу команди,
   час **у Python**: на кожен постинг створюється об'єкт `Posting`, на кожен терм — три
   `array` (440 тис. викликів). *Гіпотеза:* якщо зберігати постинги як масиви NumPy
   int32, які `np.frombuffer` бере прямо з байтів файлу (без копії й без об'єктів на
   постинг), завантаження скоротиться в рази, і лишиться розбір JSON-заголовка.
3. **Старт CLI (імпорти)** — ≈ 0,7 с `compile` і виконання модулів; `findex search`
   імпортує все, що є в `cli.py` (httpx і selectolax краулера, typer, rich), навіть коли
   вони не потрібні. Час у Python. *Гіпотеза:* ліниві імпорти (краулер — лише в
   `findex crawl`) зріжуть помітну частину старту.

**Саме ранжування (BM25/TF-IDF) — не гаряче місце на цьому корпусі.** Переписування на
NumPy, яке вимагає лаба, очікувано дасть невеликий виграш на коротких списках (накладні
витрати виклику NumPy з'їдають вигоду) і великий — на довгих.

Результати після змін — у кінці цього файлу.
